01

Identify the agent's role

The optional agent explains the selected lesson and can request a lookup. Its model chooses actions within the configured tools and limits.

02

Execute a typed tool

The catalog tool returns a record or a missing-record result. It performs the operation; a confident model answer cannot replace it.

03

Run a defined workflow

createStep and createWorkflow encode lookup then plan. createRun().start() executes that sequence in the installed Mastra runtime.

04

Inspect data between steps

Each step has an input/output schema. The planner consumes the lookup result instead of silently inventing missing fields.

05

Distinguish supplied context from memory

recentLesson comes from this request. It is visible context, not persisted conversation memory; storage-backed memory belongs in a later lesson.

06

Check business completion

The workflow can execute successfully while returning a needs-clarification business outcome. Inspect both levels before reporting success.

Check your understanding

What makes this a workflow?

The application defines and executes the sequence of typed steps. It does not rely on a model to choose the order.

Does the recentLesson field implement memory?

No. It is supplied with the current request and is not retained as conversation memory.

What should happen when lookup fails?

The application should expose a missing-record or clarification outcome rather than invent catalog data.

Implemented scope: The local path executes a real two-step Mastra workflow and deterministic planning logic. It does not call a model or persist conversation history. The separately labelled live agent uses the same bounded catalog.

Practical exercise

Change the session duration and inspect the plan. Then request a missing lesson and explain why SDK success is not the same as satisfying the user's task.
